## 2. Core principles

1. **Core is pure Swift + Foundation.** No UIKit/SpriteKit/SwiftUI/Combine/Dispatch in `FactoryCore`. It must
   build and test on Linux (`swift build && swift test` in `Core/`). Swift 6.0 toolchain, language mode 5.
2. **Deterministic fixed-step simulation at 60 UPS.** `World.step()` advances exactly one tick. No wall-clock
   time, no `Date()`, no `random()` inside the simulation — use `world.rng` (DeterministicRNG). Iterate in
   deterministic order (arrays, never `Dictionary`/`Set` iteration for logic).
3. **Data-driven.** Every number comes from `GameData.json` through `PrototypeDB` (string ids resolved to dense
   `Int` indices at load). Hot loops use indices and cached per-prototype values, never string lookups.
4. **Performance is a feature** (GDD pillar). Targets on A15: 5 000 active entities + 20 000 belt items at
   60 UPS using < 6 ms/tick. Techniques: struct-of-arrays component storage, aggregate solving (transport
   lines, fluid segments, electric networks), sleep/wake of idle entities, zero allocations per tick in steady
   state (no closures capturing in hot loops, no `[ItemStack]` temporaries per entity per tick, reuse buffers).
5. **Single-threaded world.** The World is owned by one thread (the main thread in the app, driven from
   `SKScene.update`). Rendering reads it after stepping. No locks inside Core.

## 3. Entities and systems

- `EntityStore` holds `EntityRecord`s (proto, kind, origin = top-left tile, rotated w/h, direction, flags,
  `component`, `powerSlot`, `fluidSlot`, generation, health). Entity id = `Int32` row index. UI holds
  `EntityHandle` (index+generation) and resolves it each time.
- **Direction convention:** an entity's direction is the direction items/fluids *move* out of it. A north-facing
  belt moves items north; a north-facing inserter picks from the south tile and drops to the north; a north-facing
  drill outputs north.
- Each `EntityKind` is owned by exactly one `EntitySystem` (see `World.init`). The system keeps components in
  dense arrays; `EntityRecord.component` indexes them. Swap-remove ⇒ update the moved entity's `component`.
- Cross-cutting aspects:
  - **Electric**: PowerSystem keeps an endpoint per electric entity (`powerSlot`). Consumers call
    `world.power.satisfaction(of:)` at the start of their update (σ solved this tick from last tick's requests)
    and `world.power.request(e, joules:)` for the next tick.
  - **Fluids**: FluidSystem owns all fluid boxes (`fluidSlot`), for pipes and machines alike. Machines use the
    box API (`amount/add/remove/setFilter`).
  - **Burner**: `BurnerEnergy` value type embedded in the owning component (furnace, burner drill, burner
    inserter, boiler).
  - **Modules/beacons**: machine components own their module `Inventory`; `world.beacons.beaconEffects(on:)`
    returns beacon contributions.
- **Item flow** between entities goes through `ItemEndpoint` (accept/insert/peek/extract) routed by kind via
  `world.insert/extract/...`. Belts are not endpoints; inserters/drills use `BeltSystem.insertItem/pickItem`.
- **Topology changes**: after build/remove/rotate World calls `neighborhoodChanged(rect)` on every system.
  Systems rebuild cached topology lazily (mark dirty, rebuild at start of next `update()`).
- **Update order** (`World.step`): power → fluids → mining → crafting → labs → beacons → inserters → belts →
  containers → statics → research → player → stats.

## 4. Player actions

UI never mutates the world directly. It sends `PlayerCommand`s through `world.execute(_:)` (via
`GameController.execute`). Commands validate (placement, reach, inventory, research unlocks), move items, and
record undo entries. Read-only queries (status, progress, inventories) are direct method calls on systems.

## 5. Persistence

- Binary, little-endian, sectioned format (`BinaryWriter.writeSection`) with magic `GFSV`, format version,
  metadata header (readable without loading the world: name, mode, level, play time, tick, date, thumbnail PNG).
- World section order: settings → tick/rng/bonuses → surface (generated chunks only) → entity records →
  each system in `World.systems` order → research → character → stats → session/objectives.
- Each system writes its component arrays verbatim so component indices stay valid; derived topology is rebuilt
  in `didLoad()`.
- Compression: the app layer may compress the byte buffer (Apple `Compression` LZFSE) behind
  `#if canImport(Compression)`; Core works on raw bytes and accepts a `SaveCompressor` hook.
- Autosave: rotating slots, interval from settings, plus on app backgrounding. Writes are atomic
  (write temp file → rename).

## 6. App architecture (iOS)

- SwiftUI app shell (`@main`), `RootView` routes: Main menu → New game (campaign level select / freeplay setup)
  → Load → Settings → Game.
- Game screen = `SpriteView(scene: GameScene)` + SwiftUI HUD overlay. `GameScene.update(_:)` calls
  `controller.frame(dt)` → `session.advance(realSeconds:)` → renderer sync.
- `GameController` (`@Observable`, `@MainActor`, `App/Sources/Bridge`) owns the `GameSession`, the interaction
  state (mode, selected entity, build item, direction, quickbar), and publishes a lightweight `HUDState`
  snapshot at ~10 Hz (not every frame) so SwiftUI does not re-render at 60 Hz.
- Rendering: 64 px per tile at zoom 1 (texture resolution), camera scale controls zoom. Terrain is baked per chunk
  into one texture (one SKSpriteNode per visible chunk). Entities use pooled SKSpriteNodes from one texture atlas
  (batched draws). Belt items and inserter hands drawn only for the visible rect from pooled nodes. Cull
  everything outside the camera rect + margin.
- Sprites: `Sprites.atlas` PNGs named `entity_<id>[_<dir>][_f<n>]`, `item_<id>`, `tile_<id>_v<n>`,
  `belt_<tier>_<shape>_f<n>`, `ore_<resource>_<stage>`, `ui_<name>`. `SpriteCatalog.texture(_:)` falls back to a
  generated placeholder if a sprite is missing, so rendering never blocks on art.

## 7. Team process

- Each specialist works in its own git worktree/branch and only edits files it owns (table above). Small additive
  changes to Lead-owned shared files are allowed when unavoidable — list them in your handoff note.
- Keep `cd Core && swift build && swift test` green on your branch. Add tests for every mechanic you implement,
  using the real `PrototypeDB.shared` data.
- Commit with clear messages. At the end write `docs/team/<role>.md`: what you built, public API, known gaps,
  shared-file changes, how to test.
- Use exact numbers from `docs/research`. Where the spec says **[GF]**, follow the Gearforge rule.
